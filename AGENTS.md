# AGENTS.md — working in blockudoku-rl

Guide for coding agents (Claude Code, Codex, Cursor, …) and humans. `CLAUDE.md`
imports this file; keep tool-neutral guidance here.

## What this is

A Rainbow DQN agent for Blockudoku, trained in **JAX + Equinox**, exported to
**ONNX** and played in a **static web page** (GitHub Pages) with
**onnxruntime-web**, so inference runs entirely in the visitor's browser.

## Map

```
docs/RULES.md              normative game spec (rules, scoring, action/obs layout)
configs/*.yaml             ALL hyperparameters; full.yaml sets every field, others `extends:` it
src/blockudoku/
  pieces.py                piece catalogue (source of truth for shapes/ids)
  env.py                   pure-functional jit/vmap env: reset, step, observe, action_mask
  network.py               Equinox RainbowNet: ViT (cell/piece/register tokens, 2D RoPE),
                           noisy dueling C51 heads over a log-spaced return support
  replay.py                prioritised n-step replay as a JAX pytree (time-major ring)
  rainbow.py               loss (C51 + double Q), acting, training loop (scan on GPU)
  config.py                typed schema + YAML loader (extends, --set overrides)
  train.py / evaluate.py   CLIs
  tracking.py              optional wandb logging (config `wandb:` section, credentials from .env)
  checkpoint.py            run dir <-> (RainbowNet, Config)
  export_onnx.py           hand-built ONNX graph mirroring RainbowNet (noise-free)
  sync_assets.py           regenerates web/pieces.json + RULES.md appendix
web/                       the static site (deployed as-is)
  game.js                  DOM-free JS port of env.py
  agent.js                 onnxruntime-web inference (ort module injected)
  app.js, index.html, style.css
  pieces.json              GENERATED from pieces.py
  model/model.onnx|yaml    GENERATED by export_onnx (committed; this is what ships)
tests/                     pytest; tests/reference.py is a naive oracle of RULES.md;
                           tests/js/*.mjs are driven by tests/test_web.py
runs/                      training outputs (gitignored)
```

## Commands

```bash
make install                 # uv sync + npm ci (npm is dev-only: tests run web/*.js in Node)
uv sync --extra cuda         # on the GPU machine (JAX with CUDA 12)
cp .env.example .env         # WANDB_API_KEY for experiment tracking (never commit .env)
make test                    # everything; ~1.5 min on CPU
make check                   # lint + tests + generated-asset freshness (what CI runs)
make train CONFIG=full RUN=runs/full      # GPU; CONFIG=small for a CPU run
make eval RUN=runs/small     # greedy, noise-free; compare with `make baselines`
make export RUN=runs/small   # -> web/model/
make serve                   # http://127.0.0.1:8000/
uv run python -m blockudoku.train --config full --out runs/x --set net.dim=256 --set learning_rate=5e-5
```

Baselines (256 games): random ≈ 79 points, greedy 1-ply ≈ 168.

## Contracts that must not drift

These are checked by tests. If you break one, fix all sides in the same change.

1. **Rules**: `docs/RULES.md` ⇄ `env.py` ⇄ `web/game.js` ⇄ `tests/reference.py`.
   Use the `change-game-rules` skill (`.claude/skills/change-game-rules/SKILL.md`).
2. **Pieces**: edit only `pieces.py`, then `make sync`. `sync_assets --check` fails on stale output.
3. **Action index** `slot*81 + r*9 + c` and **observation** (`planes` [4,9,9],
   `pieces` [75]) are shared by env, network, ONNX, `game.js` and `agent.js`.
4. **Network ⇄ ONNX**: every op in `RainbowNet.__call__` has a counterpart in
   `export_onnx.build_onnx`. `tests/test_export.py` (onnxruntime) and
   `tests/test_web.py::test_agent_js_matches_jax` (onnxruntime-web) check parity.
   Use the `change-network` skill.
5. **Configs are YAML only.** Dataclasses in `config.py` are a schema with *no
   defaults*; values live in `configs/`. New hyperparameter = schema field +
   value in `configs/full.yaml`. Unknown/missing keys are errors.
6. **onnxruntime-web version** is pinned in two places: `web/app.js` (CDN URLs)
   and `package.json`. Bump both together.

## Conventions

- JAX: pure functions, explicit PRNG keys (`jax.random.key`), no Python side
  effects inside jitted code; batch with `vmap`. Model code is written for a
  single example (tokens `(T, D)`), without a batch dim.
- Mixed precision: parameters and optimiser state are float32; `compute_dtype`
  casts a copy for the forward/backward pass. LayerNorm statistics, attention
  softmax and the returned logits stay float32.
- Equinox modules hold only arrays + `eqx.field(static=True)` metadata.
  `TrainState` stores `params` (array leaves); `rb.model(params)` rebuilds the module.
- Tests over prose: add a test with every behavioural change. Prefer comparing
  against `tests/reference.py` over hand-computed constants.
- Python ≥3.11 via `uv`; lint with `ruff` (`make lint`).
- Web: plain ES modules, no build step, no framework. `game.js`/`agent.js` must
  stay DOM-free so Node can test them.

## Gotchas

- PyYAML parses `3e-4` (no dot) as a string; the config loader coerces numeric
  strings for numeric fields, but write `3.0e-4` in YAML files.
- GitHub Pages cannot send COOP/COEP headers → no wasm threads; `app.js` sets
  `numThreads = 1`.
- XLA:CPU runs the model several times slower inside `lax.scan`/`fori_loop`, so
  `iteration_loop: auto` uses a Python loop on CPU and a fused scan on GPU.
- The training step donates its whole input state. Never let two `TrainState`
  leaves share one buffer (e.g. reusing one `jnp.zeros` for several fields):
  XLA rejects donating the same buffer twice.
- Value support is log-spaced (`support_scale: symlog`), so raw game points work
  as rewards (`reward_scale: 1.0`). Keep `v_max` above the discounted returns you
  expect, because values above it are clipped.
- The hand's empty slots are `-1` everywhere (env, replay, JS). Replay stores
  hands as `int8`.
- Secrets live only in `.env` (gitignored); never put keys in YAML or code. Tests use
  `wandb.mode=offline` and must not need network access or credentials.
- `evaluate.play` caps games at `max_moves`; a strong agent can hit it — check
  the `unfinished` count.
